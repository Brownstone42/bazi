# Specification: ความแข็ง–อ่อนของดิถีและธาตุให้คุณ

สถานะ: Draft สำหรับตรวจรับก่อนพัฒนา  
เวอร์ชัน: 0.1.0  
แนวทางหลัก: จื่อผิง (子平法) แบบสมดุลธาตุ  
ขอบเขต: ดวงกำเนิดบุคคลหนึ่งคน

## 1. วัตถุประสงค์

ระบบต้องประเมินโครงสร้างดวงกำเนิดอย่างตรวจสอบย้อนกลับได้ เพื่อใช้เป็นฐานของคำอ่านบุคคล ดวงคู่ เสาโชค และคำแนะนำรายวันในอนาคต

ระบบต้องตอบคำถามต่อไปนี้:

1. ดิถีอยู่ในระดับแข็ง–อ่อนใด
2. หลักฐานใดสนับสนุนหรือถ่วงดิถี
3. ดวงเป็นโครงสร้างปกติหรืออาจเป็นโครงสร้างพิเศษ
4. ดวงต้องปรับสภาพร้อน เย็น แห้ง หรือชื้นก่อนหรือไม่
5. ธาตุใดเป็นธาตุให้คุณหลัก (用神)
6. ธาตุใดเป็นธาตุสนับสนุน (喜神)
7. โครงสร้างดวงมีความชัดเจนระดับใด

เอกสารนี้ไม่ถือว่าจำนวนธาตุเพียงอย่างเดียวเพียงพอสำหรับตัดสิน และไม่แสดงคะแนนความแม่นยำแก่ผู้ใช้

## 2. คำศัพท์ที่ใช้ในผลิตภัณฑ์

| คำภายในระบบ | คำที่แสดงแก่ผู้ใช้ | ความหมาย |
|---|---|---|
| Day Master / 日主 | ดิถี | ก้านฟ้าของเสาวัน ใช้แทนเจ้าชะตา |
| Strength | กำลังของดิถี | ความสามารถของดิถีในการรับและจัดการพลังอื่นในดวง |
| Yong Shen / 用神 | ธาตุให้คุณหลัก | ธาตุที่ช่วยแก้ปัญหาหลักของโครงสร้างดวง |
| Xi Shen / 喜神 | ธาตุสนับสนุน | ธาตุที่ช่วยส่งเสริม用神หรือช่วยสร้างสมดุลรอง |
| Ji Shen / 忌神 | ธาตุที่ควรระวัง | ธาตุที่อาจทำให้ความไม่สมดุลเดิมเด่นขึ้น |
| Structure clarity | ความชัดเจนของโครงสร้างดวง | ระดับที่หลักฐานในดวงชี้ไปในทิศทางเดียวกัน |

คำว่า “ธาตุให้คุณ” ไม่ได้หมายความว่าธาตุนั้นดีในทุกวัน ทุกเสาโชค หรือทุกสถานการณ์ ต้องประเมินปฏิสัมพันธ์กับช่วงเวลานั้นอีกครั้ง

## 3. ข้อมูลนำเข้า

ระบบรับข้อมูลจาก Calculation Engine เท่านั้น:

- ก้านฟ้าและกิ่งดินทั้งสี่เสา
- ดิถี ธาตุ และหยิน–หยาง
- กิ่งเดือนและเวลาสารทฤดูที่ใช้คำนวณ
- ก้านฟ้าที่ซ่อนในแต่ละกิ่ง พร้อมลำดับพลังหลัก/กลาง/ปลาย
- สิบเทพของก้านฟ้าและก้านซ่อนทุกตัว
- การรวม ปะทะ ทำร้าย ลงโทษ และทำลาย
- ข้อมูลการแปลงธาตุ หาก Calculation Engine ยืนยันเงื่อนไขได้

ห้ามให้ Interpretation Engine คำนวณปฏิทินใหม่เอง

## 4. ผลลัพธ์มาตรฐาน

```ts
type StrengthLevel =
  | 'very_strong'
  | 'strong'
  | 'balanced'
  | 'weak'
  | 'very_weak'

type StructureClarity =
  | 'clear'
  | 'fairly_clear'
  | 'borderline'

type PatternType =
  | 'regular'
  | 'possible_follow'
  | 'possible_dominant'
  | 'requires_expert_review'

interface StrengthAssessment {
  strengthLevel: StrengthLevel
  structureClarity: StructureClarity
  patternType: PatternType
  primaryUsefulElement: Element | null
  supportiveElement: Element | null
  cautionElements: Element[]
  climateAdjustment: {
    required: boolean
    condition: 'cold' | 'hot' | 'dry' | 'damp' | null
    preferredElement: Element | null
  }
  evidence: EvidenceItem[]
  alternatives: AlternativeAssessment[]
  ruleVersion: string
}
```

คะแนนภายในใช้เพื่อทำให้กฎ deterministic และทดสอบ regression เท่านั้น ห้ามแสดงเป็น “ความแม่น 87%” หรือ “ดวงแข็ง 82%” แก่ผู้ใช้

## 5. ลำดับการประเมิน

ต้องประเมินตามลำดับต่อไปนี้ ห้ามข้ามขั้น:

### ขั้นที่ 1 — ตรวจความสมบูรณ์ของข้อมูล

- ต้องมีปี เดือน วัน และเวลาเกิด
- ต้องทราบ timezone ที่เกิด
- ต้องมีเสาทั้งสี่จาก Calculation Engine
- หากเวลาเกิดไม่แน่นอน ให้ลดความชัดเจนลงอย่างน้อยหนึ่งระดับ
- หากเกิดใกล้ขอบเขตสารทฤดูหรือเวลา 23:00 ให้เก็บ warning จาก Calculation Engine

### ขั้นที่ 2 — ตรวจ月令หรือกิ่งเดือน

กิ่งเดือนเป็นหลักฐานที่มีน้ำหนักสูงสุดในการประเมินกำลังตามฤดูกาล แต่ไม่ใช่หลักฐานเพียงข้อเดียว

สถานะตามฤดูกาลแบ่งเป็น:

- 旺 — ได้ฤดูกาลโดยตรง
- 相 — ได้แรงส่งจากฤดูกาล
- 休 — มีพลังแต่ไม่อยู่ในช่วงเด่น
- 囚 — ถูกจำกัดโดยฤดูกาล
- 死 — เสียฤดูกาลอย่างชัดเจน

ผลของขั้นนี้ต้องบันทึกเป็น evidence แยกต่างหาก เช่น:

```json
{
  "rule": "seasonal_command",
  "direction": "support",
  "weight": "major",
  "message": "ดิถีทองเกิดในเดือนระกา จึงได้กำลังจากฤดูกาลโดยตรง"
}
```

สำหรับเดือนดิน 辰 戌 丑 未 ต้องอ่านก้านซ่อนและฤดูกาลที่สืบเนื่องร่วมด้วย ห้ามถือว่าเดือนดินทั้งสี่เหมือนกันทั้งหมด หากกฎยังแยกไม่ได้ให้ลดความชัดเจนหนึ่งระดับ

### ขั้นที่ 3 — ตรวจรากของดิถี

ตรวจว่าธาตุเดียวกับดิถีปรากฏในก้านซ่อนของกิ่งใดบ้าง

ลำดับกำลังของราก:

1. รากเป็นพลังหลักของกิ่ง (本气) — แข็งแรง
2. รากเป็นพลังกลาง (中气) — ปานกลาง
3. รากเป็นพลังปลาย (余气) — อ่อน

น้ำหนักตำแหน่ง:

1. กิ่งเดือน — สำคัญต่อฤดูกาลและโครงสร้าง
2. กิ่งวัน — ยึดโยงกับดิถีโดยตรง
3. กิ่งยาม — แสดงฐานพลังที่นำไปใช้ภายหลัง
4. กิ่งปี — มีผลแต่ห่างจากดิถีมากกว่า

ห้ามนับก้านซ่อนตัวเดียวซ้ำเป็นทั้ง “ราก” และ “แรงสนับสนุน” ในผลรวมเดียวกัน ต้องเก็บได้หลายป้ายกำกับแต่มี contribution เพียงครั้งเดียว

### ขั้นที่ 4 — ตรวจแรงสนับสนุนที่เปิดเผย

พิจารณาก้านฟ้าอื่นที่:

- เป็นธาตุเดียวกับดิถี — 比肩/劫财
- ให้กำเนิดดิถี — 正印/偏印

การมีก้านฟ้าเปิดเผยมีผลชัดกว่าก้านที่ซ่อน แต่ต้องตรวจด้วยว่าก้านนั้น:

- มีรากรองรับหรือไม่
- ได้หรือเสียฤดูกาล
- ถูกผสมหรือถูกควบคุมจนทำหน้าที่ได้ลดลงหรือไม่

ก้านที่ลอยโดยไม่มีรากต้องมีน้ำหนักน้อยกว่าก้านที่มีราก

### ขั้นที่ 5 — ตรวจแรงระบายและแรงกด

แยกเป็นสามกลุ่ม:

- ดิถีให้กำเนิด — 食神/伤官 เป็นแรงระบาย
- ดิถีควบคุม — 正财/偏财 เป็นภาระที่ดิถีต้องจัดการ
- ควบคุมดิถี — 正官/七杀 เป็นแรงกดหรือกรอบควบคุม

แต่ละกลุ่มไม่ถือว่า “ไม่ดี” โดยอัตโนมัติ ความหมายขึ้นกับว่าดิถีมีกำลังพอรับหรือไม่

### ขั้นที่ 6 — ตรวจการรวมและการแปลง

- การมีคู่รวมไม่ได้แปลว่าแปลงธาตุสำเร็จเสมอ
- ต้องมีเงื่อนไขฤดูกาล ราก และพลังสนับสนุนการแปลง
- ถ้ายืนยันได้เพียงว่า “รวม” แต่ยืนยันการแปลงไม่ได้ ให้ลด availability ของตัวอักษรแต่ไม่เปลี่ยนธาตุ
- หากผลการแปลงเป็นจุดชี้ขาดต่อแข็ง–อ่อนและยังยืนยันไม่ได้ ให้ `structureClarity = borderline`

### ขั้นที่ 7 — ตรวจโครงสร้างพิเศษ

ต้องตรวจโครงสร้างพิเศษก่อนเลือก用神แบบสมดุลทั่วไป

เวอร์ชันแรกตรวจเฉพาะสัญญาณเตือน:

- ดิถีอ่อนมาก ไม่มีราก และไม่มีแรงสนับสนุนที่ใช้งานได้ → `possible_follow`
- ธาตุฝ่ายเดียวครองฤดูกาล มีรากและก้านเปิดเผยต่อเนื่อง โดยแทบไม่มีแรงต้าน → `possible_dominant`
- มีหลักฐานขัดกันหรือขึ้นกับการแปลงที่ยังยืนยันไม่ได้ → `requires_expert_review`

เวอร์ชัน 0.1 ห้ามยืนยัน従格หรือ专旺格อัตโนมัติ ให้แสดงว่า “อาจเข้าข่ายโครงสร้างพิเศษ” และยังไม่ออก用神แบบฟันธง

### ขั้นที่ 8 — จัดระดับกำลังของดิถี

| ระดับ | หลักฐานโดยรวม |
|---|---|
| แข็งมาก | ได้ฤดูกาล มีรากแข็งหลายตำแหน่ง และแรงสนับสนุนมากกว่าแรงระบาย/กดอย่างชัดเจน |
| แข็ง | ได้หลักฐานสนับสนุนชัด แต่ยังมีแรงระบายหรือควบคุมที่ทำงานได้ |
| สมดุล | แรงสนับสนุนและแรงระบาย/กดใกล้เคียงกัน ไม่มีฝ่ายใดครองชัดเจน |
| อ่อน | เสียฤดูกาลหรือรากไม่พอ และแรงระบาย/กดมากกว่าแรงสนับสนุน |
| อ่อนมาก | ไม่มีรากที่ใช้งานได้ แทบไม่มีแรงสนับสนุน และถูกระบาย/กดอย่างต่อเนื่อง |

การอยู่ใกล้รอยต่อสองระดับต้องเลือกผลหลักหนึ่งค่าและเก็บอีกค่าใน `alternatives`

### ขั้นที่ 9 — ตรวจการปรับภูมิอากาศ (调候)

ตรวจความร้อน เย็น แห้ง และชื้นของดวงแยกจากแข็ง–อ่อน

- หากสภาพสุดขั้วจนธาตุอื่นทำงานไม่ได้ ให้ธาตุปรับภูมิอากาศมีลำดับก่อน用神เพื่อสมดุล
- หากสภาพไม่สุดขั้ว ให้บันทึกเป็นคำแนะนำรอง ไม่เปลี่ยน用神หลัก
- ห้ามสรุปจากฤดูกาลเพียงอย่างเดียว ต้องดูธาตุที่ปรากฏจริงในดวงด้วย

เวอร์ชันแรกต้องใช้กฎแบบ conservative: หากยังไม่มีเกณฑ์ที่ยืนยันได้ ให้ `required = false` และเพิ่ม evidence ว่าได้ตรวจแล้วแต่ไม่พบภาวะสุดขั้ว

### ขั้นที่ 10 — เลือก用神และ喜神

สำหรับโครงสร้างปกติ:

| สภาพดิถี | ผู้สมัคร用神 |
|---|---|
| แข็งหรือแข็งมาก | ธาตุที่ระบาย ควบคุม หรือเปลี่ยนพลังให้เป็นผลลัพธ์ โดยเลือกตามสิ่งที่ดวงขาดและใช้งานได้จริง |
| สมดุล | ธาตุที่รักษาการไหลเวียนและแก้จุดติดขัด ไม่เพิ่มฝ่ายใดจนเกินไป |
| อ่อนหรืออ่อนมาก | ธาตุที่ให้กำเนิดหรือเป็นธาตุเดียวกับดิถี โดยเลือกตามฤดูกาลและความสามารถในการตั้งราก |

กฎเลือก最终:

1. แก้ปัญหาหลักของดวงได้
2. มีเส้นทางการให้กำเนิดหรือควบคุมที่ไม่สร้างปัญหาใหม่รุนแรงกว่าเดิม
3. ไม่ถูกทำลายหรือผสมจนใช้งานไม่ได้ทั้งหมด
4. หากมีผู้สมัครเท่ากัน ให้เลือกธาตุที่ช่วยการไหลเวียนของดวงก่อน
5. 喜神ต้องช่วย用神หรือช่วยให้用神ทำงาน ไม่ใช่เพียงธาตุที่ “ดูดี” แยกกัน

หากเป็น `possible_follow`, `possible_dominant` หรือ `requires_expert_review` ให้用神เป็น `null` ในเวอร์ชันแรก

## 6. ความชัดเจนของโครงสร้างดวง

### โครงสร้างชัดเจน

- หลักฐานฤดูกาล ราก และแรงสนับสนุน/ระบายชี้ไปทางเดียวกัน
- ผลไม่ขึ้นกับสมมติฐานการแปลงธาตุ
- ไม่อยู่ใกล้ขอบสารทฤดูหรือขอบเวลาเกิด
- ไม่มีผลทางเลือกที่เปลี่ยน用神

ข้อความผู้ใช้:

> โครงสร้างดวงชัดเจน หลักฐานสำคัญส่วนใหญ่ชี้ไปในทิศทางเดียวกัน

### โครงสร้างค่อนข้างชัด

- มีหลักฐานขัดกันบางส่วน แต่ข้อสรุปหลักยังไม่เปลี่ยน
- อาจอยู่ใกล้รอยต่อแข็ง/สมดุลหรือสมดุล/อ่อน
- ทางเลือกอื่นไม่ทำให้用神หลักเปลี่ยน หรือเปลี่ยนเฉพาะ喜神

ข้อความผู้ใช้:

> โครงสร้างดวงค่อนข้างชัด มีแรงบางส่วนถ่วงกัน แต่ยังเห็นแนวโน้มหลักได้

### โครงสร้างก้ำกึ่ง ต้องพิจารณาเพิ่มเติม

- ผลขึ้นกับเวลาเกิดที่ไม่แน่นอน ขอบสารทฤดู หรือการแปลงธาตุ
- เข้าข่ายโครงสร้างพิเศษ
- การเลือกผลทางเลือกทำให้用神เปลี่ยน

ข้อความผู้ใช้:

> โครงสร้างดวงมีเงื่อนไขที่ตีความได้มากกว่าหนึ่งแนวทาง ระบบจะแสดงทั้งสองความเป็นไปได้โดยไม่ฟันธง

## 7. Evidence model

ทุกข้อสรุปต้องย้อนกลับไปยังกฎและตำแหน่งในดวงได้

```ts
interface EvidenceItem {
  id: string
  rule: string
  sourcePillars: Array<'year' | 'month' | 'day' | 'hour'>
  sourceCharacters: string[]
  direction: 'support' | 'drain' | 'control' | 'neutral' | 'uncertain'
  impact: 'major' | 'medium' | 'minor'
  contribution: number
  message: string
}
```

ข้อกำหนด:

- `contribution` ใช้ภายในและอาจปรับระหว่าง calibration
- ผู้ใช้เห็น `message` ไม่เห็นตัวเลขดิบ
- หลักฐานหนึ่งรายการต้องมี ID คงที่เพื่อทำ regression test
- คำอ่านภาษาไทยต้องสร้างจาก evidence ไม่สร้างย้อนกลับจากข้อความ AI

## 8. หลักการให้คะแนนภายใน

เวอร์ชันแรกใช้ Evidence Ledger ไม่ใช้การนับจำนวนธาตุตรง ๆ

- หลักฐานระดับ `major` มีผลต่อการเปลี่ยนระดับได้โดยลำพังหนึ่งขั้นเมื่อไม่มีหลักฐานระดับ major ต้าน
- หลักฐานระดับ `medium` อย่างน้อยสองรายการในทิศเดียวกันจึงเทียบเท่า major หนึ่งรายการ
- หลักฐานระดับ `minor` ใช้ตัดสินกรณีรอยต่อ ห้ามใช้กลับผลที่มี major ชัดเจน
- เดือนและรากต้องถูกประเมินก่อนก้านเปิดเผยเสมอ
- คะแนนสุทธิเป็นเพียงตัวช่วยจัดกลุ่ม ผลสุดท้ายต้องผ่าน guardrails ของโครงสร้างพิเศษและการแปลง

น้ำหนักตัวเลขจริงจะถูกตรึงหลังทดสอบ reference charts อย่างน้อย 30 ดวง ไม่กำหนดถาวรใน Specification เวอร์ชัน 0.1

## 9. ภาษาที่อนุญาตและไม่อนุญาต

อนุญาต:

- “มีแนวโน้ม”
- “โครงสร้างสนับสนุนเรื่อง…”
- “ธาตุนี้ช่วยสร้างสมดุลในพื้นดวง”
- “ควรระวังเมื่อพลังนี้เพิ่มขึ้นมาก”

ไม่อนุญาต:

- “ธาตุนี้ดีเสมอ”
- “ใส่สีนี้แล้วจะรวย”
- “ดวงแข็งจึงเป็นคนแข็งกร้าว”
- “ความแม่น 90%”
- คำวินิจฉัยโรค การรับรองผลการลงทุน หรือการตัดสินว่าความสัมพันธ์จะสำเร็จแน่นอน

## 10. การใช้ AI

AI ใช้ได้เฉพาะ:

- เรียบเรียง evidence เป็นภาษาที่เป็นธรรมชาติ
- ปรับระดับภาษาให้เหมาะกับบริบท
- สรุปคำแนะนำจากผลที่ Rule Engine อนุมัติแล้ว

AI ห้าม:

- เปลี่ยน strength level, 用神 หรือ喜神
- สร้าง evidence ใหม่ที่ Rule Engine ไม่ได้ส่งมา
- ยืนยันโครงสร้างพิเศษเอง
- ตีความผลเป็นเหตุการณ์แน่นอน

## 11. Reference cases ที่ต้องเตรียม

ก่อนพัฒนา production rule engine ต้องมีอย่างน้อย 30 เคส:

- ดิถีแต่ละธาตุอย่างน้อย 4 เคส รวม 20 เคส
- ดวงได้ฤดูกาลแต่ไร้ราก
- ดวงเสียฤดูกาลแต่มีรากและ印มาก
- ดวงสมดุล
- เดือนดินทั้ง 辰 戌 丑 未
- ดวงที่มีคู่รวมแต่ไม่แปลง
- ดวงที่การแปลงอาจเปลี่ยนข้อสรุป
- ดวงอ่อนมากที่อาจเข้าข่าย従格
- ดวงแข็งมากที่อาจเข้าข่าย专旺格
- เวลาเกิดใกล้ 23:00
- วันเกิดใกล้ขอบสารทฤดู

แต่ละเคสต้องมี:

- input วัน เวลา timezone
- สี่เสา
- strength level ที่คาดหวัง
- หลักฐานหลักอย่างน้อยสามข้อ
- 用神/喜神ที่คาดหวังหรือเหตุผลที่ยังไม่ควรเลือก
- structure clarity ที่คาดหวัง
- ผู้ตรวจและวันที่ตรวจ

## 12. Acceptance criteria

Specification ถือว่าพร้อมพัฒนาเมื่อ:

- [ ] กฎไม่ใช้จำนวนธาตุอย่างเดียว
- [ ] แยกฤดูกาล ราก ก้านเปิดเผย และแรงระบาย/กด
- [ ] ป้องกันการนับ contribution ซ้ำ
- [ ] การรวมไม่ถูกถือว่าแปลงอัตโนมัติ
- [ ] ตรวจสัญญาณโครงสร้างพิเศษก่อนเลือก用神
- [ ] แยก调候ออกจากความแข็ง–อ่อน
- [ ] ทุกผลมี evidence ที่ย้อนตรวจได้
- [ ] ใช้คำว่า “ความชัดเจนของโครงสร้างดวง”
- [ ] กรณีก้ำกึ่งแสดงทางเลือกโดยไม่ฟันธง
- [ ] มี reference cases อย่างน้อย 30 เคสก่อนตรึงน้ำหนัก
- [ ] Rule Engine ให้ผลเดิมทุกครั้งสำหรับ input และ ruleVersion เดียวกัน
